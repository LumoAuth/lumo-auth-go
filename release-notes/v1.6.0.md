## Highlights & Fixes

### 1. Capabilities in `<resource>:<action>` Form (`capability.go`)

An agent capability is one of the agent's OAuth scope values. LumoAuth now writes every capability as `<resource>:<action>`, such as `invoices:read`, with the wildcard `invoices:*`. The SDK's capability matching follows the server again.

- `NormalizeCapability()` now returns the server's canonical form, with `:` between the parts. It trims the name, lower-cases ASCII letters, turns every `.` into `:`, collapses runs of `:` and trims `:` from both ends.
- A `-` is now part of a name, not a separator. `pull-requests:comment` is one resource and one action, and `invoices-read` is a different capability from `invoices:read`.
- A name that ends in `:*` covers every action under that prefix, at any depth, but not the prefix itself. `invoices:*` covers `invoices:read` and `invoices:read:draft`, but not `invoices`.
- A `.` is still read as `:` when the SDK compares. A dotted permission slug such as `invoices.read` matches the held `invoices:read`, and a capability stored as `invoices.*` still covers `invoices:read`.
- The same rules apply in all of these places:
  - `NormalizeCapability()`, `CapabilityCovers()` and `AnyCapabilityCovers()`
  - `Agent.HasCapability()` and `Agent.RequireCapability()`
  - `AccessTokenClaims.HasCapability()` for verified tokens
- `AccessTokenClaims.HasScope()` still compares scopes exactly.

| Input to `NormalizeCapability()` | v1.5.0 | v1.6.0 |
| :--- | :--- | :--- |
| `"Invoices:Read"` | `"invoices.read"` | `"invoices:read"` |
| `"Invoices.Read"` | `"invoices.read"` | `"invoices:read"` |
| `"invoices-read"` | `"invoices.read"` | `"invoices-read"` |

```go
lumoauth.NormalizeCapability("Pull-Requests.Comment")  // "pull-requests:comment"
lumoauth.CapabilityCovers("users:*", "USERS.DELETE")   // true
lumoauth.CapabilityCovers("users:*", "users-delete")   // false: "-" is part of a name
lumoauth.CapabilityCovers("invoices:*", "invoices")    // false
```

### 2. `RouteWebCheckEmail` Points to the Email-First API (`routes.go`)

- `Routes[RouteWebCheckEmail]` (`web.checkEmail`) is now `POST /orgs/{orgId}/api/v1/oauth/check-email`.
- Before, the route was `POST /orgs/{orgId}/check-email`. That path is the route of the hosted login page, and it does not answer other sites.
- No SDK method calls this route. The change affects only code that reads the route table directly, through `RoutePath`, `BuildPath` or `Routes`.
- The route table now matches the JavaScript SDK v1.6.0, which calls the same endpoint from `checkEmailExists()`.

The endpoint is for apps that render their own sign-in form. It reports the sign-in methods that the organization offers, so that the form can show the next step after a person types an email address. The request body is JSON with `email` and `client_id`, the client ID of an active application of the organization. A request from a browser must come from one of the allowed origins of the application.

The answer is the same for every address. It does not say whether the address has an account, so show the same next step to everyone. `exists` is `true` whenever the server answered. The flags `password_enabled`, `passkey_enabled` and `magic_link_enabled` hold the organization's methods. A refused request gets `{"error": …, "message": …}`, for example `invalid_client`, `origin_not_allowed` or `rate_limited`.

### 3. Resource-First Default Scope for Delegation (`resource_delegation.go`)

- `DelegationResource.ConsentURL()` now asks for `documents:read` when `ConsentURLParams.Scopes` is empty. Earlier releases asked for `read:documents`.
- `DelegationChain.ConsentURL()` calls this method, so it has the same default.
- Every scope, capability and Ask action in the doc comments, `doc.go` and `README.md` now puts the resource first: `documents:read`, `web:search`, `document:read`, `reports:read`.

## Upgrade Notes

- **`NormalizeCapability()` returns a different string.** It now returns `invoices:read` where v1.5.0 returned `invoices.read`. Update any code that stores or compares its output.
- **A `-` no longer matches a `:` or a `.`.** `HasCapability(ctx, "invoices-read")` is now `false` for an agent that holds `invoices:read`, and a held `users:*` no longer covers `users-delete`. This also applies to `RequireCapability()` and to `AccessTokenClaims.HasCapability()` in MCP servers. Write these names as `<resource>:<action>`.
- **Register capabilities and request scopes in `<resource>:<action>` form.** LumoAuth refuses the dot form (`invoices.read`) when you register a capability, request a scope for its API or call `Ask()`. The SDK does not check this before it sends the request.
- **The default scope for delegation changed.** If your code calls `ConsentURL()` without scopes and expects `read:documents`, pass `[]string{"read:documents"}`.
- **Requests built from `RouteWebCheckEmail` now go to the API endpoint.** Send a JSON body with `email` and `client_id`, and read the JSON answer.
- **If you check AAuth requests with `AAuthClaims.VerifyProofOfPossession()`, add your own replay checks.** The method checks the signature against the key in the token. It does not require a recent `created`, a single-use nonce or a `Content-Digest` header. The doc comment now lists the checks that LumoAuth applies to its own endpoints. This is not a change in behavior.
- `Version` is now `"1.6.0"`, so the default `User-Agent` reports `1.6.0`.
- No dependency changes in this release. The module still requires Go 1.22.

## Documentation & Tests

- Clarified the AAuth doc comments:
  - `AuthTokenParams`: LumoAuth ignores `Scope`, because the scope of the auth token comes from the resource token's `scope` claim. `RedirectURI` is required when the user has to consent, and the server answers 400 `invalid_request` without it. The request must be signed with the key in the agent token's `cnf` claim.
  - `RequestAuthToken()`: LumoAuth asks for consent with a 200 response that holds `request_token` and `authorization_uri`. LumoAuth answers 401 when it rejects the agent token or the signature.
  - `RefreshParams` and `Refresh()`: the resource token must come from the same resource as the original grant. `Scope` only narrows, and a scope outside the grant is refused with 400 `invalid_scope`. The response carries no new refresh token.
  - `ExchangeToken()`: `act.agent` names the upstream agent and `act.sub` the upstream user. A chain has at most 5 hops.
  - The signing notes in `aauth_signing.go` list the `Signature-Input` parameters that the server accepts. They also say that the SDK does not sign with EC P-256 keys, and that `VerifySignatureBase()` checks only Ed25519 and RSA signatures.
  - `SignOptions.SignatureKey` must use the label `sig1`. The agent token endpoint and `/aauth/token/revoke` need no `Signature-Key`.
  - `AAuthClaims`, `PublicJWKThumbprint()` and `JWK.Thumbprint()` describe each claim and where LumoAuth uses the thumbprint (`agent_jkt`, `cnf_jkt`).
- `README.md` says that LumoAuth ignores `AuthTokenParams.Scope`, and that `Refresh()` needs a resource token from the same resource.
- `routes_drift_test.go` no longer lists `RouteWebCheckEmail` in `knownDrift`. The server's OpenAPI spec documents the new path, so `TestRoutesExistInOpenAPISpec` now checks this route like every other route. Only `RouteWellKnownAAuthIssuer` stays a known exception.
- `capability_test.go` checks the new form, the `:*` wildcard and the rule for `-`. It also runs the shared contract cases in `sdk-contract/vectors/agent-capabilities.json`, which are now in the `<resource>:<action>` form.
- Added `TestDelegationChainConsentURLDefaultScope` to `delegation_chain_test.go`. The other tests now use resource-first scopes, capabilities and actions.
- Added the release notes for v1.5.0 (`release-notes/v1.5.0.md`).
